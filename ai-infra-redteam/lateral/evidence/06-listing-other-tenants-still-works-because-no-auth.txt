=== does chroma expose a global admin/list-all-tenants endpoint reachable with no auth? ===
GET /api/v2/tenants -> 405: 
GET /api/v2/auth/identity -> 200: {"user_id":"","tenant":"default_tenant","databases":["default_database"]}

Interpretation: because Chroma requires no authentication at all, the
foothold does not need to be handed tenant_a's name or collection UUID by
any side channel. Listing itself is correctly scoped (per vectordb/FINDINGS.md:
GET .../tenant_a/databases/db_a/collections only returns tenant_a's own
collections, never leaking tenant_b's), but since there is no credential
gating WHICH tenant/database path a caller may address, an attacker can
simply try plausible tenant/database names directly and list that tenant's
collections outright - no UUID leak, side channel, or guessing needed. This
is a materially easier path than the vectordb component's original framing
(which required the UUID to already be known). Combined with the vectordb
finding that /get and /query then ignore tenant scoping entirely, this
means concretely: an attacker who reaches Chroma at all, with no
credentials, can enumerate every tenant/database name that exists by
trying strings (there is nothing stopping a `/api/v2/tenants/<guess>` probe
loop) and read every collection under each one.
'/api/v2/tenants' (GET, list-all) returns 405 (method not allowed) - Chroma
does not expose a single "list every tenant" endpoint, so a working attack
does still require some way of knowing or guessing candidate tenant names;
it does not require the collection UUID once a tenant/database name is
correctly guessed.
