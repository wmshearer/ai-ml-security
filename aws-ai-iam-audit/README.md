# AWS AI IAM Policy Audit

**This is a static policy analysis project, not a penetration test.** No AWS
account was used. No AWS service was scanned, probed, or attacked. Nothing was
exploited or bypassed. Every input file is AWS's own public documentation.
Every output file in `evidence/` is real, captured tool output that you can
regenerate by running the scripts in this repo.

## What this is

AWS publishes the full JSON of every AWS managed IAM policy for free, with no
account required, at `docs.aws.amazon.com/aws-managed-policy/`. This project
fetches the managed policies attached to Amazon Bedrock and Amazon SageMaker,
runs them through three established open-source IAM policy analyzers
(cloudsplaining, parliament, policy_sentry), and adds a small custom analyzer
that looks for three specific structural patterns those generic tools do not
name directly:

1. An `iam:PassRole` grant scoped to *any role in the account*.
2. A permission condition that depends on a resource tag, where the tag can
   be set by the same principal the condition is meant to restrict.
3. A grant whose Resource covers every S3 bucket in every account.

The project then connects that structural analysis to a real, disclosed, and
already-patched AWS vulnerability chain (CVE-2026-8597 and CVE-2026-8596) to
argue that the *class* of risk these policy structures create is not
theoretical: AWS's own advisory shows that write access to a model artifact
location plus permission to run inference against it was, in a real shipped
version of the SageMaker Python SDK, enough to get code execution.

## Result up front

Across the 8 fetched AI-related managed policies:

- **3** `iam:PassRole` statements grant PassRole against a wildcard role
  Resource (`arn:aws:iam::*:role/*`) rather than a scoped role name pattern.
  One of these is in `AmazonSageMakerFullAccess` (Sid
  `AllowPassRoleToSageMaker`); two are in `AmazonSageMakerCanvasFullAccess`.
- **2** statements grant `s3:GetObject` against every bucket in the account
  (`arn:aws:s3:::*`), gated only by a tag on the object
  (`s3:ExistingObjectTag/SageMaker` = `true`, or the equivalent Service
  Catalog tag) -- both in `AmazonSageMakerFullAccess`.
- **14** statements across the corpus gate permissions on a resource or
  request tag that the same class of principal can set on their own
  resources, including the Bedrock/SageMaker Marketplace endpoint statements
  in `AmazonBedrockFullAccess` gated on `aws:ResourceTag/sagemaker-sdk:bedrock`
  = `compatible`.
- **42** Allow statements across the corpus grant access with `Resource: "*"`
  (no ARN scoping of any kind) -- these are spread across every policy in the
  corpus except the two ReadOnly policies, `AmazonSageMakerFullAccess`, and
  `AmazonSageMakerModelGovernanceUseAccess`... see the counts below for which
  specific policies.
- **`AmazonBedrockReadOnly`** and **`AmazonSageMakerReadOnly`** produced
  **zero** cloudsplaining findings. This is reported because a clean result
  is a real result, not because it was expected.

Every one of these numbers is generated by `src/analyze.py` from the fetched
JSON and is pinned by a test in `tests/test_policies.py`. See
[What was found](#what-was-found-full-numbers) below for the complete table.

## How to run this

Requires Python 3.13 (parliament's `pkg_resources` dependency does not import
cleanly under 3.14 in this environment; see [Limits](#limits)). System Python
on most distributions is "externally managed," so this project uses a venv.

```bash
cd aws-ai-iam-audit
python3.13 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install cloudsplaining parliament "setuptools<81" policy_sentry requests pytest

# 1. Fetch the real policy JSON from AWS's public docs (no AWS account needed)
.venv/bin/python src/fetch_policies.py

# 2. Run the generic analyzers and capture their real output
mkdir -p evidence/cloudsplaining evidence/parliament
for f in policies/*.json; do
  case "$f" in *.meta.json|*_fetch_summary.json) continue;; esac
  name=$(basename "$f" .json)
  .venv/bin/cloudsplaining scan-policy-file --input-file "$f" -v > "evidence/cloudsplaining/${name}.txt" 2>&1
  .venv/bin/parliament < "$f" > "evidence/parliament/${name}.txt" 2>&1
  .venv/bin/parliament --json < "$f" > "evidence/parliament/${name}.jsonl" 2>/dev/null
done

# 3. Initialize policy_sentry's local IAM action/ARN database, then query it
.venv/bin/policy_sentry initialize
.venv/bin/policy_sentry query action-table --service iam --name PassRole

# 4. Run the custom structural analyzer
.venv/bin/python src/analyze.py

# 5. Run the tests
.venv/bin/pytest tests/ -v
```

`setuptools<81` is pinned deliberately: setuptools removed `pkg_resources`
(which parliament imports) starting around version 81, and modern `pip`
no longer installs setuptools into a venv by default. Without the pin,
`parliament --help` fails with `ModuleNotFoundError: No module named
'pkg_resources'`.

### The two statements this project is built around

From `AmazonSageMakerFullAccess.json`, exactly as fetched:

```json
{
  "Sid": "AllowPassRoleToSageMaker",
  "Effect": "Allow",
  "Action": ["iam:PassRole"],
  "Resource": "arn:aws:iam::*:role/*",
  "Condition": {
    "StringEquals": { "iam:PassedToService": "sagemaker.amazonaws.com" }
  }
}
```

```json
{
  "Sid": "AllowS3GetObjectWithSageMakerExistingObjectTag",
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": ["arn:aws:s3:::*"],
  "Condition": {
    "StringEqualsIgnoreCase": { "s3:ExistingObjectTag/SageMaker": "true" }
  }
}
```

The `iam:PassedToService` condition is real and does something: it stops a
principal from passing a role to an arbitrary AWS service. It does not stop
the principal from passing *any* role in the account to SageMaker
specifically, as long as that role exists. `policy_sentry`'s own IAM action
database shows that `iam:PassRole` supports a scoped resource format
(`arn:${Partition}:iam::${Account}:role/${RoleNameWithPath}`) -- see
`evidence/policy_sentry/iam_PassRole.txt` -- so a narrower Resource was an
available option; the managed policy uses the widest form of that scoped
pattern (`role/*`) instead.

The S3 statement similarly could have been scoped to specific bucket ARNs
(`policy_sentry` shows `s3:GetObject` supports
`arn:${Partition}:s3:::${BucketName}/${ObjectName}` -- see
`evidence/policy_sentry/s3_GetObject.txt`) but instead uses `arn:aws:s3:::*`,
meaning the only thing standing between this grant and any object in any
bucket in the account is a single tag key equal to `true`, and tagging is
something the object's owner typically controls.

From `AmazonBedrockFullAccess.json`:

```json
{
  "Sid": "MarketplaceModelEndpointMutatingAPIs",
  "Effect": "Allow",
  "Action": [
    "sagemaker:CreateEndpoint", "sagemaker:CreateEndpointConfig",
    "sagemaker:CreateModel", "sagemaker:DeleteEndpoint", "sagemaker:UpdateEndpoint"
  ],
  "Resource": [
    "arn:aws:sagemaker:*:*:endpoint/*",
    "arn:aws:sagemaker:*:*:endpoint-config/*",
    "arn:aws:sagemaker:*:*:model/*"
  ],
  "Condition": {
    "StringEquals": {
      "aws:CalledViaLast": "bedrock.amazonaws.com",
      "aws:ResourceTag/sagemaker-sdk:bedrock": "compatible"
    }
  }
}
```

This is the tag-gated SageMaker-endpoint-via-Bedrock statement. The tag key
here is `sagemaker-sdk:bedrock`, and its required value is the literal string
`compatible`. A separate statement in the same policy
(`MarketplaceModelEndpointAddTagsOperations`) grants `sagemaker:AddTags`
constrained to only setting that exact tag value alongside two other required
tags (`bedrock:marketplace-registration-status` = `registered` and
`sagemaker-studio:hub-content-arn` matching AWS's own public model hub ARN
pattern). So in the current policy text, setting the "compatible" tag also
requires setting a tag whose value must match an AWS-controlled hub content
ARN pattern -- this narrows, but does not eliminate, the concern that the
security boundary runs partly through attacker-controlled tag state. This is
recorded in `evidence/analyze_findings.json` as three separate tag-gated
statements (`MarketplaceModelEndpointMutatingAPIs`,
`MarketplaceModelEndpointAddTagsOperations`,
`MarketplaceModelEndpointDeleteTagsOperations`,
`MarketplaceModelEndpointInvokingOperations`) rather than collapsed into one
generic claim.

AWS documents a related, general defense for exactly this class of problem
(a downstream service like SageMaker being invoked "on behalf of" Bedrock)
using `aws:SourceArn`/`aws:SourceAccount` confused-deputy conditions:
https://docs.aws.amazon.com/bedrock/latest/userguide/cross-service-confused-deputy-prevention.html
The statements above use `aws:CalledViaLast` for a related purpose (confirming
the call chain went through Bedrock), which is a different condition key
from the confused-deputy pattern AWS documents on that page; it is included
here as the source AWS points to when discussing this general risk category
for Bedrock, not as a description of the mechanism these specific SageMaker
statements use.

## What the CVE chain shows

CVE-2026-8597 and CVE-2026-8596 are AWS's own disclosed and **already
patched** findings in the SageMaker Python SDK, not something this project
discovered, reproduced, or tested against a live account.

- **CVE-2026-8597** (CVSS 6.4, per NVD): the SageMaker Python SDK's Triton
  inference handler deserialized model artifacts using `pickle` without
  integrity verification. A principal with S3 write access to the model
  artifact path could replace the artifact with a crafted pickle payload and
  get code execution inside the inference container. Affected versions
  v2.199.0-v2.257.1 and v3.0.0-v3.7.1; fixed in v2.257.2 and v3.8.0.
  Sources: https://aws.amazon.com/security/security-bulletins/2026-031-aws/
  and https://github.com/aws/sagemaker-python-sdk/security/advisories/GHSA-rq6v-x3j8-7qgf
- **CVE-2026-8596** (CVSS 8.5, per NVD): a companion flaw in the same
  affected version range. The HMAC key used to sign artifact integrity checks
  (`SAGEMAKER_SERVE_SECRET_KEY`) was stored in cleartext in an environment
  variable retrievable via Describe APIs, so an attacker who could read that
  variable could forge a valid signature and defeat the very integrity check
  meant to prevent CVE-2026-8597.
  Advisory: https://github.com/aws/sagemaker-python-sdk/security/advisories/GHSA-7hh5-prp2-mfh5

Neither CVE was found, reproduced, or tested in this project. They are cited
because they demonstrate, with AWS's own advisory as the source, that the
*impact class* this project's policy analysis is concerned with -- a
principal with S3 write access to a model artifact location, plus permission
to run inference against that artifact, ending in code execution inside an
inference container -- is a real outcome that has actually happened in AWS's
own software, not a hypothetical. The policy structures documented above
(wildcard PassRole to SageMaker, any-bucket tagged-object S3 access, tag-gated
endpoint permissions) describe IAM conditions under which a principal could
plausibly reach that kind of artifact-write-plus-invoke position. They do not
prove any current SageMaker or Bedrock software is vulnerable today; the SDK
flaw that made that combination dangerous in this specific way has been
fixed since v2.257.2 / v3.8.0.

## Tests

`tests/test_policies.py` pins:

- that the four required policies (SageMaker/Bedrock Full/ReadOnly) were
  actually fetched and are well-formed IAM policy documents,
- that `AllowPassRoleToSageMaker` exists in `AmazonSageMakerFullAccess` with
  exactly the wildcard Resource and condition described above,
- that `AllowS3GetObjectWithSageMakerExistingObjectTag` exists with exactly
  the any-bucket Resource and tag condition described above,
- that `BedrockAll` in `AmazonBedrockFullAccess` grants `bedrock:*` on `*`,
- that the tag-gated SageMaker-endpoint-via-Bedrock statement exists with the
  `sagemaker-sdk:bedrock` = `compatible` condition,
- the exact counts produced by `src/analyze.py` for all four structural
  checks,
- that no fabricated CVE ID appears in this README.

If AWS changes any of these policies, the corresponding test should fail the
next time `fetch_policies.py` and `analyze.py` are re-run. That is the
intended behavior, not a bug to fix by loosening the assertion.

Run: `.venv/bin/pytest tests/ -v`

## Limits

- **No AWS account was used anywhere in this project.** All input data is
  AWS's own public documentation, fetched over plain HTTPS with no
  credentials.
- **Nothing was attacked, scanned, or exploited.** No AWS API was called
  except to fetch public documentation pages.
- **No novel vulnerability was discovered.** The two CVEs cited
  (CVE-2026-8597, CVE-2026-8596) are AWS's own disclosed findings, already
  fixed in shipped SageMaker Python SDK versions. This project did not find,
  confirm, or reproduce either one.
- **No live IAM boundary was ever tested.** All analysis is static: it reads
  the JSON text of managed policies and checks structural patterns in that
  text. Whether a specific account's actual configuration (SCPs, permission
  boundaries, other identity-based policies layered on top, resource
  policies) would allow the theoretical paths described here is not
  something this project can or does determine, because no account was
  examined.
- **The tag-gate mitigations in `AmazonBedrockFullAccess` are more layered
  than a single tag check.** Setting the `compatible` tag also requires
  setting a second tag whose value must match an AWS-controlled ARN pattern
  for the public model hub. This project reports the tag-gated conditions as
  found, without claiming the tag boundary is trivially defeatable in the
  current policy text.
- **Development environment note:** parliament's dependency on
  `pkg_resources` does not import cleanly under Python 3.14 with a
  default `pip install` in a venv (no bundled setuptools, and setuptools
  >=81 removed `pkg_resources`). This project's venv uses Python 3.13 and
  pins `setuptools<81`. If a policy's markdown reference page structure ever
  changes such that `src/fetch_policies.py`'s regex-based extraction breaks,
  the script reports the specific policy that failed and continues with the
  rest rather than silently emitting a partial or hand-edited file -- but
  that fallback was not needed for this run; all 8 requested policies were
  fetched successfully.
