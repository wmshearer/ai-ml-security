# Findings

Every number below traces to a file under `evidence/`. None are recomputed
by hand; the scoring numbers come from `scripts/05_score.py` reading the raw
scanner output in `evidence/{picklescan,modelscan,fickling}/raw_results.json`
against `corpus/manifest.csv`.

## 1. The corpus and its ground truth

`corpus/manifest.csv` lists all 10 corpus files with their class, the
technique used, the CVE reproduced (if any), and the expected detection
outcome. Generated by `scripts/01_generate_corpus.py`, which writes every
file using only Python's standard library `pickle` module. No file is
downloaded from anywhere.

- **6 `benign` files**: plain dicts, lists, tuples, a set, numbers, an empty
  dict. Confirmed by static opcode inspection
  (`tests/test_corpus.py::test_benign_files_have_no_reduce_opcode`) to
  contain no `REDUCE` opcode, meaning no callable is ever invoked when one
  of these is unpickled.
- **2 `poc_overt` files**: `__reduce__` payloads with no evasion attempted.
  One names `corpus_gen.marker.write_marker` (this project's own helper)
  directly. The other names `posixpath.join`, a real Python standard
  library function, to test whether a scanner flags any non-builtin
  callable or only a fixed list of known-dangerous names. Both confirmed by
  static opcode inspection to contain a `REDUCE` opcode
  (`tests/test_corpus.py::test_poc_files_do_contain_reduce_opcode`).
- **2 `poc_evasive` files**: reproductions of CVE-2025-10155 and
  CVE-2025-10157 (see section 3).

`corpus_gen/marker/__init__.py` defines `write_marker(name)`, the only
function any payload in this corpus ever calls. Its entire effect is
appending one timestamped line to `evidence/markers/marker_log.txt`, a
directory inside this project that is excluded from git (`.gitignore`).
`corpus_gen/marker/submodule.py` defines a second function,
`write_marker_via_submodule`, that does the same thing, and exists only so a
pickled `GLOBAL` opcode can name a real submodule path
(`corpus_gen.marker.submodule`) for the CVE-2025-10157 reproduction.

## 2. Confirming the mechanism without unpickling

`evidence/pickletools_dis/` holds the output of `pickletools.dis()`, Python's
standard-library opcode disassembler, run against every corpus file. This is
static analysis: `pickletools.dis()` reads and prints opcodes, it does not
execute any of them.

Example, `corpus/poc_overt/poc_overt_reduce.pkl`
(`evidence/pickletools_dis/poc_overt/poc_overt_reduce.pkl.dis.txt`):

```
11: SHORT_BINUNICODE 'corpus_gen.marker'
31: SHORT_BINUNICODE 'write_marker'
46: STACK_GLOBAL
48: SHORT_BINUNICODE 'poc_overt_reduce'
67: TUPLE1
69: R    REDUCE
```

`STACK_GLOBAL` (the pickle protocol 4 opcode for naming an importable
object, called `GLOBAL` in older protocol versions) resolves
`corpus_gen.marker.write_marker`; `REDUCE` calls it with the string
`'poc_overt_reduce'` as its one argument. This is the entire mechanism every
malicious pickle relies on: name a callable, then call it. This project's
version of that callable only appends a line to a log file.

The CVE-2025-10157 reproduction
(`evidence/pickletools_dis/poc_evasive/cve_2025_10157_submodule_import.pkl.dis.txt`)
shows the same shape with a submodule path:
`corpus_gen.marker.submodule.write_marker_via_submodule`, confirmed by
`tests/test_corpus.py::test_submodule_import_file_names_a_real_submodule`.

## 3. The two CVE reproductions, in mechanism detail

**CVE-2025-10155** (NVD, CVSS 9.3, "Improper Input Validation"): JFrog's
published research describes picklescan versions up to and including 0.0.30
branching on file extension before content in `scan_bytes()`. A file with a
PyTorch-style extension (`.bin`, `.pt`) was routed into PyTorch-container
parsing logic; when that parsing failed on a plain, non-container pickle
stream, the scan produced no findings instead of falling back to a generic
pickle scan.

This project's reproduction,
`corpus/poc_evasive/cve_2025_10155_extension_mismatch.bin`, is the exact
same pickle bytes as `poc_overt_reduce.pkl` above, saved with a `.bin`
extension instead of `.pkl`. Confirmed by
`tests/test_corpus.py::test_extension_mismatch_file_has_non_pickle_extension`.

**CVE-2025-10157** (NVD, CVSS 9.3, "Protection Mechanism Failure"): JFrog's
published research describes picklescan's unsafe-globals check using exact
string matching against a denylist of module names. A `GLOBAL` opcode
naming a submodule of a denylisted module (JFrog's own example:
`asyncio.unix_events` instead of `asyncio`) did not match the denylisted
top-level name exactly, so picklescan scored it "suspicious" rather than
"dangerous" and did not fail the scan.

This project's reproduction,
`corpus/poc_evasive/cve_2025_10157_submodule_import.pkl`, names
`corpus_gen.marker.submodule.write_marker_via_submodule`: a genuine
submodule of `corpus_gen.marker`, standing in for the disclosed
submodule-of-a-denylisted-module shape, resolving only to this project's
own inert marker function.

Both CVEs were fixed in picklescan 0.0.31. The version installed and scored
in this project is **1.0.5** (confirmed:
`evidence/picklescan/raw_results.json`, field `"version"`), which is far
past the fix. Whether the reproductions still evaded picklescan at this
version is an empirical question this project answered by running the scan,
not an assumption; see section 5.

## 4. Running each scanner

`scripts/02_run_picklescan.py`, `scripts/03_run_modelscan.py`, and
`scripts/04_run_fickling.py` each run their tool once per corpus file
(picklescan runs twice per file: once in default mode, once with
`--strict`) and save the tool's own raw stdout/stderr plus, where the tool
supports it, parsed JSON, under `evidence/<tool>/raw_results.json`.

**A real bug found and fixed while building the modelscan runner:**
modelscan's `-r json` output is printed through the `rich` library's
console, which line-wraps text at terminal width by inserting literal
newlines inside JSON string values. The first version of
`scripts/03_run_modelscan.py` parsed this with `json.loads()` and silently
caught the resulting `JSONDecodeError`, defaulting to "0 issues found" on
parse failure. On this corpus that default happened to match modelscan's
real result (modelscan really did find 0 issues everywhere, see section 5),
but the code could not tell a parse failure from a genuine clean scan, which
means it could have silently reported "0 issues" on a file modelscan
actually flagged. Fixed by setting `COLUMNS=2000` in the subprocess
environment (rich's line-wrap width follows the `COLUMNS` environment
variable) and by making `scripts/05_score.py` raise an error instead of
defaulting to 0 if a modelscan result still fails to parse. Caught by
writing `tests/test_scanner_evidence.py::test_fickling_json_output_parses_for_every_result`
and the equivalent manual check on modelscan's evidence file, not by a
scanner disagreement.

## 5. Detection results, per tool, per class

Full detail: `evidence/scoring/per_file_results.csv` (one row per corpus
file) and `evidence/scoring/summary_by_tool_and_class.csv` (aggregated by
tool and class). No number in this section is a blended average across
tools or across classes; both files keep them separate throughout.

### picklescan 1.0.5

- **Zero false positives**: picklescan raised no suspicious or dangerous
  global on any of the 6 benign files, in either default or `--strict` mode.
- **picklescan flagged 2 of 2 `poc_overt` files.** In default mode both
  callables (`corpus_gen.marker.write_marker`, `posixpath.join`) were
  listed as "suspicious" globals; exit code stayed 0 (picklescan's default
  mode does not fail the process on a merely-suspicious global, only on a
  "dangerous" one). In `--strict` mode, both were promoted to "dangerous"
  and picklescan exited 1 ("infected"). This project counts a "suspicious"
  listing as a detection because the tool did surface the callable by name;
  a user reading picklescan's own summary output would see it either way,
  even though only `--strict` mode fails the process.
- **picklescan flagged 2 of 2 `poc_evasive` files** (the CVE-2025-10155 and
  CVE-2025-10157 reproductions), in both modes. **The disclosed bypasses did
  not reproduce.** This is the expected result for a picklescan version this
  far past the 0.0.31 fix, and it is reported as a finding, not a failure of
  this project: it shows the fix holds at the version actually installed.
  Source: `evidence/picklescan/raw_results.json`, both files show
  `"Suspicious globals: 1"` (default) and `"dangerous import ... FOUND"`
  (`--strict`), identical in shape to the non-evasive `poc_overt_reduce.pkl`
  result.

### modelscan 0.8.8

- **Zero false positives**: modelscan reported `total_issues: 0` on all 6
  benign files.
- **modelscan flagged 0 of 2 `poc_overt` files and 0 of 2 `poc_evasive`
  files.** Every payload file in this corpus scored `total_issues: 0`.
  Source: `evidence/modelscan/raw_results.json`.
- **Why, read from modelscan's own source**:
  `.venv/lib/python3.12/site-packages/modelscan/settings.py` defines
  `unsafe_globals` as a fixed dictionary of module names (`os`, `nt`,
  `posix`, `socket`, `subprocess`, `sys`, `runpy`, `pickle`, `_pickle`,
  `bdb`, `pdb`, `shutil`, `asyncio`, plus a `builtins`/`__builtin__`
  function list and a short `HIGH`-severity list). `corpus_gen.marker`,
  this project's own module, was never going to be on that list, so
  `poc_overt_reduce.pkl` and both CVE reproductions were invisible to
  modelscan's `PickleUnsafeOpScan` by design, not by a bug in modelscan or
  a mistake in this corpus.
- **A second, more informative miss**: `poc_overt_stdlib_global.pkl` calls
  `os.path.join`, which sits under `os`, a module modelscan explicitly
  denylists with `"*"` (meaning every attribute is treated as dangerous).
  This file was still missed. Python's own pickler resolves `os.path.join`
  to its true defining module, `posixpath` (`os.path` is an alias for
  `posixpath` on this platform), and pickles the `GLOBAL` opcode as
  `posixpath.join`, not `os.path.join`. `posixpath` is not itself on
  modelscan's denylist, even though `os` is. Confirmed by
  `evidence/pickletools_dis/poc_overt/poc_overt_stdlib_global.pkl.dis.txt`,
  which shows `SHORT_BINUNICODE 'posixpath'`, not `'os'`. This is a real,
  measured gap between "the module a Python developer would type" and "the
  module name pickle actually stores," and it means a denylist keyed on the
  familiar top-level name can miss a call that a user would describe as
  "calling something in `os`."

### fickling 0.1.12

- **Zero false positives**: all 6 benign files scored `LIKELY_SAFE`.
- **fickling flagged 2 of 2 `poc_overt` files.** `poc_overt_reduce.pkl`
  scored `LIKELY_UNSAFE` ("imports a Python module that is not a part of
  the standard library"). `poc_overt_stdlib_global.pkl` (the
  `posixpath.join` case) scored `SUSPICIOUS` rather than `LIKELY_UNSAFE`,
  because `posixpath` is part of the standard library and fickling's
  strongest rule does not fire on it; fickling instead flagged the pickle
  for assigning a call result to a variable that is never used afterward, a
  separate heuristic. Both results are non-`LIKELY_SAFE`, so both count as
  detected in this project's scoring, but the two files were not caught by
  the same rule inside fickling, and this write-up keeps that distinction
  rather than collapsing it into one "detected" bucket. Source:
  `evidence/fickling/raw_results.json`.
- **fickling flagged 2 of 2 `poc_evasive` files**, both `LIKELY_UNSAFE` for
  the same "non-standard-library import" reason as the overt case.
  **Neither disclosed bypass reproduced against fickling.** This is
  consistent with fickling's detection rule not depending on file extension
  (unlike CVE-2025-10155's mechanism) or exact module-name matching (unlike
  CVE-2025-10157's mechanism): fickling's rule is "is the imported module
  part of the standard library," which the extension change does not
  affect and the submodule path does not satisfy either.

## 6. What the three-way comparison shows about detection design

Two structurally different strategies are visible in this corpus:

- **Denylist matching** (modelscan, and picklescan's `--strict` promotion
  logic): flag a fixed set of module names known to be dangerous. Fast and
  precise against known targets, but a payload naming any module outside
  that list, including this project's own harmless helper module, is
  invisible by construction. The `posixpath` versus `os` mismatch shows
  this can misfire even for a genuinely denylisted module, if the resolved
  import path differs from the name a person would type.
- **Allowlist / origin matching** (fickling's core rule): flag anything
  that is not part of a known-safe set (the standard library), rather than
  flagging a known-dangerous set. This catches both this project's harmless
  custom module and a real dangerous one, because neither is in the
  standard library, and it does not depend on which specific dangerous
  function is called. picklescan's own suspicious/dangerous split works
  similarly in spirit: anything not explicitly known-safe is at least
  "suspicious."

Neither strategy is shown here to be better in general. The corpus in this
project never tested a payload naming an actually denylisted function like
`os.system` directly (doing so would mean building something closer to a
functioning weapon than an inert proof of concept), so this project cannot
say how modelscan performs against the payload shapes it is actually
designed to catch. What it can say, with evidence, is that modelscan's
design leaves a harmless custom-module payload, and even one specific
stdlib-resolved call, completely unflagged, while fickling and picklescan
both caught every payload shape actually built here.

## Uncertainties and things not verified further

- **modelscan's denylist-targeted detection was not tested.** This project
  never built a payload naming a function that is actually on modelscan's
  denylist (for example `os.system`), because doing so risks building
  something closer to a real weapon than an inert proof of concept. The 0
  of 4 result for modelscan in this project should be read as "modelscan
  did not catch the payload shapes this project built," not as "modelscan
  cannot catch anything."
- **fickling's and modelscan's own changelogs were not audited** for
  whether either has ever specifically patched a gap corresponding to
  picklescan's CVE-2025-10155/-10157 mechanisms. This project scored
  observed, empirical behavior at the versions actually installed
  (fickling 0.1.12, modelscan 0.8.8), not vendor claims either way.
- **The `posixpath` versus `os` naming gap** (section 5) was found by
  reading `pickletools.dis()` output during this project, not predicted in
  advance. It is reported here because it changed what the corpus actually
  measures for that one file, from "does modelscan catch an `os` call" to
  "does modelscan catch a `posixpath` call," and the distinction matters
  for reading the result correctly.
- **Corpus size is small by design** (10 files, 2 CVE reproductions). This
  project measures specific, named technique classes with a clear
  mechanism, not statistical coverage across many random payload variants.
  A single miss or catch per technique is the whole result for that row;
  there is no larger sample behind each cell in the summary table.
